# 检索精度提升指南（分工 1）

> 面向：负责检索精度提升的同学。
> 目标：在不接大模型的前提下，让「算法搜索」的 Top-K 命中更准、更稳。
> 本文所有改动点都对应仓库现有代码，可直接落地。

## 〇、先看清你现在手里有什么（现状盘点）

当前检索链路（代码已读完，以下行号对应当前 `main`）：

| 环节 | 位置 | 现状 |
|------|------|------|
| 嵌入文本构造 | `backend/parser.py:323` `_build_summary()` | 极简摘要：`{family} algorithm for {task}. Class name: {name}.` + docstring 前 2 句 + 参数 |
| 生成向量 | `backend/parser.py:373` `_get_model()` / `:382` `embed()` | 本地 `all-MiniLM-L6-v2`（384 维，通用模型），`normalize_embeddings=True`；有 `EMBEDDING_API_KEY` 走 API |
| 关键词分 | `backend/retrieval.py:41` `MATCH...AGAINST(%s IN BOOLEAN MODE)` | MySQL FULLTEXT，**布尔模式**（命中即 1，未命中即 0，无打分梯度） |
| 语义分 | `backend/retrieval.py:59` `parser.cosine(qvec, emb)` | 归一化向量点积 |
| 融合 | `backend/retrieval.py:81-85` | 语义分与关键词分各自 **min-max 归一化** → **0.5 / 0.5 加权** → 排序 |
| 候选集 | `backend/retrieval.py:73` | `algorithms` + `functions` 全表参与打分（无查询预筛） |
| 评估 | `backend/eval_test.py:13` `EVAL_QUERIES` / `:65` `evaluate()` | 8 条查询，算 MRR + Hit@1/3/5 |

**两个已存在的硬伤（改之前先知道）：**
1. `IN BOOLEAN MODE` 对 "logistic regression" 这类短查询几乎给不出梯度分，关键词分量实际上接近失效 → 检索被语义分量独大。
2. 0.5/0.5 + min-max 归一化是拍脑袋的，且候选集全表归一化会把 MiniLM 的微小差异放大成噪声。

## 一、七个可调整方向（按「性价比」排序）

| # | 方向 | 难度 | 预期收益 | 改哪里 |
|---|------|------|----------|--------|
| 1 | 扩充嵌入文本 `_build_summary` | 低 | 高 | `parser.py:323` |
| 2 | 查询改写（query rewrite）再 embed | 低 | 高 | `retrieval.py:16` |
| 3 | 重排序（rerank top-N） | 中 | 高 | 新增 `rerank()` in `retrieval.py` |
| 4 | 融合改 RRF（免调权） | 低 | 中 | `retrieval.py:81-85` |
| 5 | 换代码专用嵌入模型 | 中 | 中-高 | `parser.py:373` |
| 6 | 关键词分改自然语言/BM25 式 | 中 | 中 | `retrieval.py:41` |
| 7 | 元数据软加权（family/task 微推） | 低 | 低-中 | `retrieval.py` 融合处 |

---

### 方向 1：扩充嵌入文本（最便宜、最该先做）
**原理**：现在每个 chunk 用来生成向量的只有一句话摘要。把 `math_methods`、结构化数学公式 `docstring_math`、`references`、参数都塞进嵌入文本，向量里就有更多「可匹配信号」，语义召回立刻变好。
**改法**：`backend/parser.py` 的 `_build_summary(name, family, task, doc, params)` 里，把 chunk 已有的 `math_methods` / `docstring_math` 接进去（这两个字段 `extract_chunks` 已经抽好了，只是没进嵌入文本）。
**验证**：直接跑评估（见第三节），看 MRR / Hit@k 是否涨。

### 方向 2：查询改写（query rewrite）
**原理**：嵌入文本是「自然语言算法描述」，但用户查的是 "logistic regression"。两者不在同一表达空间 → 语义匹配差。把查询改写成与 `_build_summary` 同构的描述再 embed，召回率会明显提升。
**改法**：在 `backend/retrieval.py:16`（`qvec = parser.embed(req.query)` 之前）加一个 `rewrite_query(req.query)`，例如 "logistic regression" → "Generalized Linear Models algorithm for classification. Class name: LogisticRegression." 可用 `FAMILY_MAP` / `MATH_TERMS` 做轻量映射，不必上 LLM。
**验证**：评估 + 手动 `debug_search` 看 Top-1 是否更合理。

### 方向 3：重排序（reranker，精度提升最大头）
**原理**：检索标准范式是「召回 → 重排」。先用现有混合检索出 Top-20，再用一个 cross-encoder 对 (query, candidate) 逐对打分重排取 Top-K。cross-encoder 比 bi-encoder（MiniLM）准得多，是工业界把精度拉满的常规操作。
**改法**：在 `retrieval.py` 新增 `rerank(query, candidates, k)`，用 `sentence-transformers` 的 `cross-encoder/ms-marco-MiniLM-L-6-v2`（已装 sentence-transformers，可直接用）。`run_search` 改为「融合取前 20 → rerank → 取 top_k」。
**验证**：对比加 rerank 前后的 MRR，通常 +0.1~0.2。

### 方向 4：融合改 RRF（Reciprocal Rank Fusion）
**原理**：0.5/0.5 是手动调权，且 min-max 对短查询不稳定。RRF 公式 `score = Σ 1/(k+rank)`（k 通常取 60）直接合并两套排序，无需调权重、对分数尺度不敏感，是混合检索的稳妥替代。
**改法**：`retrieval.py:81-85` 改为分别按语义分、关键词分排出 rank，再用 RRF 合并。
**验证**：MRR 对比。

### 方向 5：换代码专用嵌入模型
**原理**：`all-MiniLM-L6-v2` 是通用句向量，对代码/算法名匹配不是最优。代码检索专用模型（CodeBERT 系、或中文友好的 `bge` / `e5`）通常更好。
**改法**：`parser.py:373` 换模型名；或设 `EMBEDDING_API_KEY` + `EMBEDDING_MODEL=text-embedding-3-small` 走 API（更省本地算力）。注意换模型后**必须重算全部向量**（重新跑 `index_repo` 导入）。
**验证**：重导后跑评估，对比基线。

### 方向 6：关键词分改进
**原理**：`IN BOOLEAN MODE` 无打分梯度。改 `NATURAL LANGUAGE MODE` 可得连续相关度；或引入同义词词典（classification↔classifier、regression↔regressor）做查询扩展。
**改法**：`retrieval.py:41` 改模式；或在 `parser.py` 加同义词展开后拼进查询。

### 方向 7：元数据软加权
**原理**：`module/family/task` 现在是硬过滤，可改为「命中即微推」的软信号，缓解过滤过死。
**改法**：融合分里加 `0.05 * match_boost`。

## 二、第一周推荐执行顺序（配合你「一周出初版」的节点）

1. **先做方向 1 + 2**（半天内，纯文本改造，零依赖）→ 跑评估看基线提升。
2. **再做方向 4（RRF）**（半天，替换融合逻辑）→ 去手调权、更稳。
3. **上方向 3（reranker）**（1 天，装 cross-encoder）→ 精度最大头。
4. 方向 5/6/7 作为「有余力再冲」，且每个都要先有评估数字背书再合。

> 铁律：每改一个方向，**先跑评估对比**，数字涨了才进分支；别凭感觉合。评估集见第三节。

## 三、怎么评估（这是精度的「尺子」，没有它等于盲改）

评估脚本已就绪：`backend/eval_test.py`。

**扩充实评测集**（现在只有 8 条，太少，结论不稳）：
- 打开 `backend/eval_test.py:13` 的 `EVAL_QUERIES`，按真实用户会怎么搜，补到 **20~40 条**，每条标注期望命中的 `module` / `algorithm`（算法名取 `algorithms` 表的 `name`，如 `LogisticRegression`）。
- 覆盖三类查询：① 算法名直搜（logistic regression）② 任务描述搜（我想做分类用什么）③ 数学方法搜（em algorithm / gradient descent）。

**运行评估**（MySQL 起来后）：
```bash
cd code-x-ray
source .venv/bin/activate
python -c "from backend import eval_test; import json; print(json.dumps(eval_test.evaluate(), ensure_ascii=False, indent=2))"
```
关注三个数：**MRR**（整体排序质量）、**Hit@1**（首条即对的比例）、**Hit@5**（前 5 有对的）。每次改动前后都记下来做对照表。

**验证单条检索**（调试用）：
```bash
python -c "from backend import retrieval, eval_test; print(retrieval.debug_search(eval_test._req({'query':'logistic regression','module':'','family':'','task':''}, top_k=10)))"
```

## 四、操作工作流（接仓库现有 Git 规范）

1. 开分支：`git checkout -b feat/retrieval`（检索精度专属，不与他人冲突）。
2. 改 `backend/retrieval.py` / `backend/parser.py` / `backend/eval_test.py`。
3. 本地跑评估，记录 MRR 前后对比。
4. 提交：`git commit -m "feat(retrieval): RRF 融合 + query rewrite，MRR 0.xx→0.yy"`。
5. 推分支 → 提 PR → 让负责评估测试的同学（分工 3）review 后合并。
6. **别动** `app.py` / `db.py` / `learn.py` / `index_pipeline.py`（别人的文件）。

## 五、怎么学（按 2~3 小时/块的低成本探针，不恋战）

1. **检索基础（必读）**：BM25 是什么、为什么比布尔匹配好 → 再读「稠密检索」与「混合检索」概念。约 2 小时。
2. **reranker 范式（重点）**：读懂「召回 bi-encoder → 重排 cross-encoder」为什么有效。约 2 小时。
3. **代码检索特殊性**：为什么通用句向量对代码不够好，CodeBERT / 代码嵌入思路。约 1.5 小时。
4. **embedding 模型选型**：bge / e5 / MiniLM 差异，何时该换。约 1 小时。
5. 边读边在你仓库上试方向 1~4，用评估数字验证理解，**不要先读一大堆再动手**。

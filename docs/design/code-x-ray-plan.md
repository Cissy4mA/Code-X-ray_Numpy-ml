## 1. 项目一句话定义

**给定一个代码仓库（链接或文件夹），把里面成千上万个函数/类切分、向量化、存入数据库，用户用自然语言（中文/英文）提问，系统精准检索出最相关的代码片段，并可选接入大模型给出解释。**

本质：把"看不懂的代码"变成"可检索、可问答的知识库"。

## 4. 当前 Demo 已知问题（必须解决）

1. **必须输全函数名才精准**：本地哈希只做"词重合"，输入近义描述（如"算订单总价"）匹配不到 `calculate_order_total`。→ 需真实语义 Embedding。
2. **中文搜不到英文代码**：代码全英文，中文 query（如"报表"）与英文函数名无 token 重叠。→ 需跨语言/多语言 Embedding，或 query 翻译。
3. **问答模块等于检索**：未接 LLM，Ask 只是把 Search 结果拼出来。→ 接大模型 API 才真正"问答"。
4. **数据量太小**：13 个函数无法体现"考古"价值。→ 见 Q1 数据集方案。

## 5. 待解答疑问 + 判断

### Q1：上万函数的数据集，能否找到并导入？

**能，且很容易。** 单个 GitHub 大仓库就远超此量级：

- Linux kernel ≈ 20 万+ 函数；Chromium、VS Code、TensorFlow、Django、React 均在数万~数十万函数级。
- 公开代码语料：CodeSearchNet（6 语言、约 600 万函数）、The Stack（约 3TB 代码）。

**落地方案**：用 GitHub API 拉取目标仓库 → `tree-sitter` 按语言解析 → 批量切分入库。Demo 阶段可先取 1~2 个中等仓库（如 Flask + Django 共约 1.5 万函数）验证到"万级"。

### Q2：公网用户需要自己搭 PHP / 后端吗？

**不需要。** 用户只需要在浏览器打开一个 URL：

- 后端（FastAPI）部署到云服务器（阿里云 ECS / 腾讯云 / Railway / Render）。
- 前端静态托管（Vercel / GitHub Pages / Netlify）。
- 数据库用云 MySQL 或 PostgreSQL（+ 向量扩展）。
- **phpMyAdmin 只是我们本地调试数据库的可视化工具，不是产品的一部分**，用户完全无感。

### Q3：小组要不要统一用 phpMyAdmin / MySQL？

**研发期不需要全员装 phpMyAdmin。** 厘清概念：

- **phpMyAdmin**：MySQL 的 Web 管理界面，调试工具，非项目依赖。任何人想看库可用 DBeaver / 命令行 / 项目自带前端。
- **数据库选型**：建议团队统一用 **MySQL 或 PostgreSQL**（二者课程都覆盖，且支持 FULLTEXT / 向量）。SQLite 也能跑，但**不支持原生 FULLTEXT 倒排索引**（需 FTS5 扩展），且与课程 SQL 示例不一致，不推荐作为统一底座。
- 结论：**数据库统一 MySQL/PostgreSQL 即可，phpMyAdmin 个人随意**。

### Q4：开发模式——只在本机搞，还是先上公网协同？

**判断正确：本机开发，部署后团队访问同一公网实例。**

- 不需要每人本地搭环境；代码用 Git 管理，部署用 CI/CD。
- 本地做开发验证，稳定后部署到一台云服务器，组员通过 URL 直接使用与反馈。
- 协同发生在"产品层面"（共用一个公网系统），不是"环境层面"（每人装一套）。

## 6. RAG 在项目中起的作用

RAG = Retrieval-Augmented Generation（检索增强生成）。在本项目里的链路：

```
用户提问（自然语言）
   ↓
① 检索 Retrieve：把问题向量化，从数据库找出 Top-K 相关代码片段（混合检索）
   ↓
② 增强 Augment：把 Top-K 片段拼进 Prompt 作为上下文
   ↓
③ 生成 Generate：大模型基于上下文回答（问答模块）；检索模块本身独立可用
```

**核心作用**：让大模型"先查资料再回答"，避免幻觉，且回答可溯源到具体函数（引用编号）。本项目里"检索"是承重墙，"生成"是加分项。

## 7. 技术难点与重点

1. **代码切分策略（Chunking）**：按什么粒度切？函数/类/逻辑块？切太碎丢失上下文，切太粗引入噪音。生产用 `tree-sitter` 多语言。
2. **跨语言检索**：中文 query → 英文代码。需跨语言/多语言 Embedding（如 bge-m3、jina-embeddings、text-embedding-3 多语言版）或 query 翻译。
3. **代码 Embedding 模型选择**：通用文本模型对代码标识符（camelCase、API 名）不敏感；代码专用模型（CodeBERT、UnixCoder、开源 jina-code）更优。
4. **混合检索融合**：关键词（FULLTEXT / BM25）+ 向量语义，如何加权、归一化、排序。
5. **大规模向量检索**：上万→百万函数时，MySQL 暴力算余弦不可行，需向量数据库 / ANN（pgvector、Milvus、Faiss）。
6. **检索质量评估**：用什么指标衡量"找得准"？Recall@K、MRR、NDCG。
7. **大模型接入与 Prompt**：代码问答的 Prompt 设计、引用格式、成本控制。
8. **部署与公网可用性**：前后端分离、云数据库、零安装体验。

## 10. 代码 RAG vs 文本 RAG：存储与检索的区别（重点）

| 对比项       | 文本 RAG（论文/文档）         | 代码 RAG（本项目）                                 |
| --------- | --------------------- | ------------------------------------------- |
| **切分单位**  | 段落 / 句子 / 滑动窗口（无结构边界） | 函数 / 类 / 逻辑块（有 AST 结构边界）                    |
| **存储内容**  | 纯文本段落 + 少量元数据（来源、页码）  | 代码块 + 丰富元数据：语言、文件路径、起止行、**调用关系、标识符、AST**    |
| **关键词检索** | BM25，处理自然语言词          | 需处理代码标识符：`camelCase`/`snake_case`、API 名、跨语言 |
| **语义向量**  | 通用文本 Embedding        | 代码专用 / 跨语言 Embedding（保留语法与标识符语义）            |
| **相关性定义** | 主题相似                  | 功能相似 / 调用相关 / 语义等价（更复杂）                     |
| **跨语言**   | 通常同语言                 | 常需中文 query → 英文代码（跨语言鸿沟）                    |
| **评估**    | 段落相关性较直观              | "相关函数"定义模糊，评估更难                             |

### 代码的特别之处（为什么不能直接套文本 RAG）

1. **半结构化**：代码有 AST、类型、调用图，可提取**结构特征**（不仅是文本）。例如"谁调用了这个函数"是文本没有的信息。
2. **标识符即语义**：`getUserOrders` 比其描述更精确，但本地哈希/中文 query 无法匹配——这是本项目当前 demo 失效的根因，也是接 Embedding API 要解决的核心。
3. **粒度敏感**：函数级 / 行级 / 文件级切分，粒度直接影响检索质量，需根据场景调。
4. **跨语言鸿沟**：用户用中文问，代码是英文标识符，必须靠跨语言或多语言模型桥接。
5. **评估复杂**：两个函数"相关"可能是语义相似、可能是调用关系、可能是功能相同——定义比文本难。

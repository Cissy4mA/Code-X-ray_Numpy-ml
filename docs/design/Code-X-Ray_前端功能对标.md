# Code X-Ray · 前端功能对标（图书馆系统类比）

> 目的：用历年数据库课程作业（图书馆/检索系统）为参照，明确我们代码检索系统的**对标规模**与**前端该补的功能**，为《数据存储与检索》20% 课程作业定边界。

---

## 一、历年同类作业怎么做的（调研结论）

### 1.1 典型形态
- **关系库 + 多表 + CRUD + 多条件查询** 是绝对主流。
- 库表一般 6–8 张：book / author / category / member / loan / fine / log / borrow_history 等。
- 评分硬指标（来自多所高校课程大纲）：
  - 画 E-R 图，实体 ≥ 3 个
  - 关系模式满足 **第三范式（3NF）**
  - 有**触发器 / 存储过程 / 视图**
  - 外键约束保证数据一致性
  - 写设计报告（6000 字以上，含需求分析/概念设计/逻辑设计/实现/测试）

### 1.2 前端普遍比想象中丰富
以查到的 Flask+Vue 图书系统为例，前端含：
- **首页仪表盘**：图书总数 / 借阅总数 / 用户总数 + 图书类型分布饼图 + 借阅状态分布 + 高价图书排行
- **多条件检索**：书名 / 作者 / 分类 组合过滤 + 重置
- **图书详情页**：封面 / 描述 / 状态
- **热门 TOP10 排行榜**、借阅历史、按热门推荐
- **管理员 CRUD**：图书/用户/分类/借阅 增删改查

> 关键认知：**评分看的是"功能完整 + 设计规范"，不是数据量大。** 示例 demo 只有 12 本书、10 个用户，照样能拿分。

## 二、对标规模测算

| 维度 | 图书馆系统 | Code X-Ray（建议） |
|---|---|---|
| 核心实体 | 书 / 作者 / 分类 / 借阅人 | 文件 / 函数 / 类 / 调用边 |
| Demo 数据量 | 十几~几十本书 | **50–150 文件、500–1500 代码块** |
| 存储 | MySQL 表 | MySQL（embedding_json + FULLTEXT） |
| 工业级参照 | — | stellaris 实测 341 文件 / 430 chunks；CodeAtlas 支持 7 语言 |

**甜区建议（受 8GB + MySQL 约束）**：
- 直接 **dogfood 自己的 Code-X-Ray 仓库** + 1 个示例 FastAPI 项目，凑到几百个 chunk。
- 不要追多语言 / 大 FAISS 索引（机器扛不住），Python + FastAPI Web 服务类 已足够。

## 三、功能映射：图书馆能查什么 ↔ 代码检索能查什么

| 图书馆可查 | Code X-Ray 可查 | 前端呈现 |
|---|---|---|
| 书名 | 函数 / 类 / 方法名（符号搜索） | 搜索框 + 自动补全 |
| 作者 | 所属模块 / 文件 / 服务子包 | 面包屑 + 文件树 |
| 分类 | 代码层（路由/service/model/前端组件） | 层过滤器 |
| ISBN | 文件路径 + 行号（精确坐标） | 详情页定位 |
| 出版社 | 所属包（auth/、orders/） | 包维度聚合 |
| 库存状态（在库/借出） | 被引用 / 调用活跃度 | 引用数标记 |
| 借阅记录 | git 修改历史 | 时间线 |
| 热门图书 TOP10 | 被引用最多 / 最复杂 Top N | 排行榜 |
| 评分 / 评论 | 圈复杂度 / 代码质量指标 | 复杂度标签 |

## 四、前端该补的功能（按优先级）

### 核心（必做，覆盖"功能完整 + 设计规范 + 差异化"）
- **A. 概览仪表盘**：文件数 / 函数数 / 类数 / 语言分布饼图 / 层分布 / 平均复杂度。对应图书馆首页统计。
- **B. 多条件检索面板**：自然语言 + 符号名 + 文件路径 + 层 + 引用数阈值 组合过滤。对应"多条件查询"。
- **C. 符号详情页**：点开函数看 源码 / 签名 / docstring / 入边（谁调用我）/ 出边（我调用谁）/ 所在文件行号 / 复杂度。对应"图书详情页"。
- **D. 热点排行榜**：被引用 Top N、复杂度 Top N、最近修改 Top N。对应"热门图书 TOP10"。
- **F. 检索可解释面板（独特卖点）**：把 向量头 / 余弦分 / 关键词分 / 融合分 全摊开。图书馆做不到、你能做的"透视"，是你"RAG 不是黑盒"叙事的地基。

### 进阶（加分项）
- **E. 调用关系图**：函数/模块调用图（可交互）。对应"分类树形结构"。
- **G. 检索质量实验页**：Recall@k / MRR 对比 naive vs endpoint-level 切分。对应"报表分析"，是你 20% 作业的**学术贡献页**。

---

## 五、推荐实现顺序

1. **A 仪表盘** —— 最快出"功能完整"观感，复用现有 `/api/stats`。
2. **B 多条件检索** —— 在现有问答框上加过滤维度，后端加 WHERE 条件。
3. **C 符号详情页** —— 需要后端补"调用边"接口（你 `parser.py` 已能抽引用，存表即可）。
4. **D 排行榜** —— 直接 SQL 聚合（按引用数 / 复杂度排序）。
5. **F 可解释面板** —— 把 backend 已有余弦/关键词分结构暴露到前端。
6. **E / G** —— 有余力再做。

## 六、一句话定位（答辩用）
> "主流图书馆作业考的是'关系建模 + 多条件检索 + 报表'；我们把它搬到了代码域——用 MySQL 同时存结构化元数据（文件/符号/层/引用边）和向量，既满足课程对关系库与查询的要求，又借 RAG 把'检索可解释性'这个图书馆系统没有的维度做出来。"

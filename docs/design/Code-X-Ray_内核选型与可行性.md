# Code X-Ray · 内核选型与可行性评估（ML/算法库方向）

> 用户决策：把"代码图书馆"的内容聚焦在 **ML/算法库（sklearn 风、偏数学类算法）** 上，个人也用得上。  
> 本文回答：能不能做？研发/测试阶段导入哪个 GitHub 仓库作为"代码图书馆"的内核？

---

## 一、可行性结论

**能做，且 ML/算法库比 Web 服务更适合"类型感知切分"这个论点。**

关键约束（选型的分水岭）：

| 仓库               | 语言构成                                   | 我们的 `ast` 解析器能吃吗         | 数学实现能索引到吗                   |
| ---------------- | -------------------------------------- | ------------------------ | --------------------------- |
| **scikit-learn** | 75%+ 是 Cython `.pyx`（数值内核），`.py` 只是薄包装 | 只能解析 `.py`，**跳过 `.pyx`** | ❌ 数学在 `.pyx` 里，索引不到         |
| **numpy-ml**     | 纯 NumPy，62 个 `.py`，零 Cython            | ✅ 开箱即用                   | ✅ 数学在 `.py` 的 docstring/注释里 |

> 用户目标是"检索偏数学类的 ML 算法"。若选 sklearn，索引到的只是 API 描述、索引不到数学内核——**舍本逐末**。故选 numpy-ml。

---

## 二、内核选型推荐

### ✅ 主选：`ddbourgin/numpy-ml`

- 地址：`https://github.com/ddbourgin/numpy-ml`
- 规模：62 个 `.py` 文件、~30 个主流算法 + 15 个工具、3 万+ 行、**纯 NumPy（+少量 SciPy）、无 Cython**
- 算法分 11 类：GMM / HMM / LDA / 神经网络 / 树模型 / 线性模型 / n-gram / 强化学习 / 非参数 / 预处理 / 工具
- 作者原话："显式地进行了所有梯度计算，以突出概念/数学的清晰性" —— 数学味最浓，正中对口
- 优势：
  1. 纯 Python → `ast` 解析器直接吃，无需为 `.pyx` 写额外解析器
  2. 数学在 docstring/注释 → 嵌入 docstring（而非裸代码）即差异化卖点
  3. 自包含算法 → 天然干净的可检索单元，不用跨文件拼
  4. 规模刚好 → 切完约 300–500 chunk，8GB + MySQL 扛得住

### ⚠️ 备选（不推荐主用）：`scikit-learn` 子集

- 如 `sklearn/linear_model` + `sklearn/cluster` + `sklearn/decomposition`
- 名气大、辨识度高，但**只能索引 `.py` API 层，索引不到 `.pyx` 数学内核**
- 若要"熟悉感"，可取其小子集做**对照实验**，但明确接受上述短板

## 三、ML 专用切分设计（贡献点）

检索单元 = **算法/估计器类**（非任意函数）：

- 类名 + 所属类别（目录：linear_models / tree_based / neural_nets / …）
- docstring 里的数学规范：目标函数、假设前提、参数分布、参考文献
- `__init__` 参数 schema + fit / predict / sample 方法签名

引用边：

- 类 → 基类（继承）
- 类 → 导入的工具函数
- 文件内方法调用边

### 可演示的数学向查询（Web 服务 RAG 讲不出来）

- "哪个算法用 EM 估计参数？" → LDA / GMM
- "logistic regression 的梯度下降实现在哪？"
- "哪些模型假设特征服从高斯分布？"
- "show me the backprop implementation" → `neural_nets/layer.py`
